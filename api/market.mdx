---
title: "Marketplace API"
description: "Browse optional namespace listings, prepare a purchase and read sale history."
---

These routes are available **when the marketplace is enabled on a deployment**. Otherwise they return `409 market_disabled`.

The marketplace uses an operator-controlled escrow account. Read the [marketplace guide](/platform/marketplace) before paying; its settlement process is separate from Allocator namespace claim fees.

## Listings and intent

### Browse listings

```http
GET /v1/market/listings
```

Returns the escrow account in the top-level `escrow` field and up to 100 active `listings`, newest first. Each listing contains `id`, `namespace`, `node`, `priceXlm`, `feeBps` and `listedAt`. This endpoint has no pagination cursor.

### Prepare a purchase

```http
POST /v1/market/listings/{id}/intent
Content-Type: application/json
```

```json
{ "account": "YOUR_G_ACCOUNT" }
```

Replace `YOUR_G_ACCOUNT` with a valid classic G account you control. The response contains:

| Object | Fields |
| --- | --- |
| `intent` | `id`, `expiresAt` |
| `pay` | `to`, `asset: "native"`, `amountXlm`, `memoType: "hash"`, `memoHash`, `note` |
| `settlement` | Namespace `node`, `seller` and ordered `steps` |

Use the exact amount, destination and hash memo returned in `pay`. The same listing/buyer pair receives the same unexpired intent. Creating an intent does not pay for or transfer the namespace.

Complete the purchase in this order:

1. Verify a current Registry namespace transfer proposal from the seller to your account.
2. Send the full amount in one native XLM payment with the intent's hash memo.
3. Accept the namespace transfer with your own authorization.

Use a self-custody sending account: refunds return to the account that sent the payment.

Invalid buyer addresses return `400 invalid_account`. Unavailable listings and intent conflicts return `409` with an `error` code. The intent route is rate-limited. If it returns `intent_conflict`, retry the request; do not send another payment to resolve the conflict.

## Settlement and refunds

Verified delivery releases the sale proceeds minus the displayed fee and returns an eligible seller bond. Seller non-delivery during a funded sale can refund the buyer and slash the bond. A buyer's failure to accept a standing proposal follows a separate outcome. See the [settlement rules](/platform/marketplace).

Partial payments do not accumulate toward the price. Underpayments and overpayment surpluses follow refund rules. Small or uncertain payouts may require operator review, so refund timing is not guaranteed.

## Sale history

```http
GET /v1/market/history/{node}
```

Use the namespace's 64-character hex namehash as `node`. The response contains the normalized `node` and up to 50 recent `sales`, newest first. Each sale includes `namespace`, `priceXlm`, `seller`, `buyer`, `settledAt` and `badge`.

Invalid hashes return `400 invalid_node`. Sales flagged as wash trading are excluded. These hosted records are informational provenance and may not cover every sale.

Selling and listing use authenticated owner-only console flows. Registry ownership and current transfer state remain authoritative.
