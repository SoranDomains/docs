---
title: "Resolving names and payments"
description: "Preserve optional memos, reject unknown legacy instructions and recheck before paying."
---

Use `resolvePayment(name)` for payments. It returns one atomic instruction from the current on-chain namespace Resolver through Universal Lookup.

<Note>
These examples require Lookup **0.6.0**, pending npm publication. Its M-address behavior is unavailable in older packages. Use the live [contract ABI](/api/onchain-resolution) or [HTTP payment endpoint](/api/resolution) while waiting; [release status](/reference/release-status) tracks availability.
</Note>

```ts
const payment = await soran.resolvePayment("Alice.Nova");
// { address, memo }
const unchanged = await soran.verifyPayment("alice.nova", payment);
if (!unchanged) throw new Error("Review the new instructions before sending");
```

## Memos are optional

| SDK memo | Meaning |
| --- | --- |
| `{ type: "none" }` | No memo in this Soran instruction |
| `{ type: "id", value: "123456" }` | Canonical decimal unsigned 64-bit ID, kept as a string |
| `{ type: "text", value: "customer-123" }` | Exact UTF-8 text, 1–28 bytes |
| `{ type: "hash", value: "…" }` | Exactly 32 bytes represented by 64 lowercase hex characters |

Ordinary native records without a current-generation payment configuration return their ordinary address with `none`. Holders do not have to create a memo to use Soran. Once a record has been configured, a persistent marker prevents lost instructions from being mistaken for that ordinary default. Removing a memo requires an explicit complete `setPayment` with `none`.

The four memo variants above are supported for `G...` addresses. `M...` and `C...` destinations support `none` only. An M address preserves its embedded muxed ID; `none` does not remove that ID. Return-hash memos and contract-specific routing arguments are outside this ABI. The SDK never substitutes G plus memo for M. See [supported address types and complete examples](/concepts/payment-destinations), including how a muxed ID differs from a transaction memo. Unknown memo types must be refused.

## Native and legacy results

```ts
const result = await soran.lookup("alice.nova");
if (result.kind === "nativePayment") {
  console.log(result.payment.address, result.payment.memo);
} else {
  // Informational legacy address; memo requirements remain UNKNOWN.
  console.log(result.address, result.memoCapability);
}
```

Both variants contain the canonical name, Registrar, optional Resolver and exact `bigint` generation. Lookup supports a legacy implementation only when the deployed configuration explicitly recognizes its current code hashes. A legacy address is not a memo-free payment instruction.

`resolvePayment`, `verifyPayment` and payment fields in `details`/`identity` reject legacy results with `LEGACY_MEMO_UNKNOWN`. Missing, malformed, archived or unreadable native instructions fail; no error retries through an older ABI or substitutes a Registrar address.

## Address-only convenience methods

`resolve(name)`, `record(name)` and `verify(name,address)` are restricted to native memo-free instructions. They reject a required memo with `PAYMENT_REQUIRED` and an unknown legacy memo with `LEGACY_MEMO_UNKNOWN`. For a muxed record, these updated SDK methods return or compare the complete M address. The older on-chain address methods cannot represent M and reject it. Prefer `resolvePayment` for general payment integration.

```ts
const address = await soran.resolve("alice.nova");
// Only succeeds with an address when the native instruction is memo-free.
```

## Building a payment

Display and preserve the whole returned tuple. A `G...` or `M...` recipient can receive a compatible classic Stellar Payment; preserve the full M destination. A `C...` recipient needs a supported Soroban asset/token transfer flow. A classic transaction contains one memo, so multiple incompatible memos require separate transactions.

Honor recipient account memo-required settings such as [SEP-29](https://github.com/stellar/stellar-protocol/blob/master/ecosystem/sep-0029.md). A Soran `none` instruction does not override that requirement.

Rechecking immediately before confirmation detects stale client data. It does not atomically bind a later classic payment to that lookup: holders can update instructions before settlement. Even a permanent Resolver permits holder record changes. An exchange using a customer memo still needs a wallet integration that includes that memo in the outgoing payment.

## Metadata is a separate read

`nameMetadata` supplies holder, built-in target, generation, expiry and active status without requiring a valid payment record. The built-in target can differ from the Resolver's effective address. Use it for ownership displays, never as a fallback payment destination.
