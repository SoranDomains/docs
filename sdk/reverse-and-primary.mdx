---
title: "Reverse and Primary names"
description: "Verify account display names through Universal Lookup without confusing customers and shared accounts."
---

A forward lookup starts with a name. A reverse lookup starts with an address and asks for a currently verified display name.

Universal Lookup exposes both namespace-scoped `reverse(namespace,address)` and cross-namespace `primary_name(address)`. SDK methods route through those calls in universal mode.

```ts
const scoped = await soran.reverse("nova", address);
const primary = await soran.primaryOf(address);
const preferred = await soran.reverseLookup(address, ["nova", "acme"]);
const candidates = await soran.reverseNames(address, ["nova", "acme"]);
```

## How verification works

A returned name must be canonical, active, in the expected namespace and forward-resolve to the requested address with current generation and routing. A required memo is allowed in this account identity proof. It remains part of the separate payment instruction.

**Primary and reverse identify an account.** They do not identify an individual customer or subaccount behind a pooled exchange address. A customer's name and memo should not be presented as the identity of everyone using that address.

These account inputs accept G or C, not muxed M addresses. Native muxed payment support does not add M account identity. A name that now pays to M cannot serve as a forward proof for the base G account, so an earlier reverse/Primary election can stop verifying. Decoding M to its base G account changes the question to that shared account's identity; it does not provide a customer-specific reverse result. See [muxed-address limits](/concepts/payment-destinations#muxed-accounts-what-is-and-is-not-supported).

A Primary record is elected by its address. Holders cannot elect a primary for a destination they do not control merely because they own a name that points there.

## Discovery scope

`reverseLookup` tries Primary first, then ordered namespace candidates. Candidates can come from its argument, `reverseNamespaces`, or a configured indexer hint. `reverseNames` checks those candidates and includes a verified Primary when available. Neither method enumerates every namespace on chain.

The old HTTP `/v1/reverse/:address` route is a **holder hint**, not the source of these verified reverse answers. Holdings and reverse records answer different questions.

## Absence and failures

A successful `primaryOf` returning `null` means there is no currently verified election returned by Primary. The existing Primary ABI may hide failed dependent proof reads behind `None`, so even this direct method cannot distinguish every absence from every internal failure. Resolver reverse has a similar limitation. A nonempty answer is independently forward-checked.

Lookup-level errors, including missing Primary configuration, still throw. `reverseLookup` and `reverseNames` can recover from a Primary failure by probing namespace candidates; failed namespace probes are not fabricated empty results.

`primaryId: null` disables Primary. A custom Primary must match the Registry anchor, and in universal mode an explicitly supplied ID must match Lookup's configured Primary. Use the [Holder SDK](/holder/managing-your-name) for address-authorized reverse and Primary writes.
