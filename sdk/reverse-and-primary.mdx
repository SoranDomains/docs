A forward lookup starts with a name. A reverse lookup starts with an address and asks for a currently verified display name.

Universal Lookup exposes namespace-scoped and cross-namespace display-name reads. For G/C addresses, it uses `reverse(namespace,address)` and `primary_name(address)`. The muxed identity extension adds separate reads keyed by the complete base G account and muxed ID.

<Note>
Muxed reverse and Primary support is live on testnet with Lookup SDK 0.8.0 and `muxed_identity_version() == 1`. Lookup was upgraded at its existing address on 7 September 2026; older packages need an explicit update. See [release status](/reference/release-status) for the verified code hash and package versions.
</Note>

```ts
const scoped = await soran.reverse("nova", address);
const primary = await soran.primaryOf(address);
const preferred = await soran.reverseLookup(address, ["nova", "acme"]);
const candidates = await soran.reverseNames(address, ["nova", "acme"]);
```

## How verification works

A returned name must be canonical, active, in the expected namespace and forward-resolve to the requested address with current generation and routing. A required memo is allowed in this account identity proof. It remains part of the separate payment instruction.

**G/C Primary and reverse identify an account.** They do not identify an individual customer or subaccount behind a pooled exchange address. A customer's name and memo should not be presented as the identity of everyone using that address.

A muxed lookup asks about the **complete M destination**. The same G account with ID `"0"`, ID `"420"` and ID `"18446744073709551615"` has three separate elections. None falls back to the G account, another ID, or a G-plus-memo route. A name that now pays to M cannot serve as a forward proof for the base G account.

The underlying G account authorizes each M election. If an exchange controls that account, the exchange must sign; a deposit customer cannot elect a name merely because the exchange gave them an M address. This proves an account-authorized display name for a payment route, not a person's real-world identity. A separate transaction memo is not part of M identity.

```ts
import { encodeMuxedAddress } from "@sorandomains/lookup";

const account = "GA7QYNF7SOWQ3GLR2BGMZEHXAVIRZA4KVWLTJJFC7MGXUA74P7UJVSGZ";
const m0 = encodeMuxedAddress(account, "0");
const m420 = encodeMuxedAddress(account, "420");
const mMax = encodeMuxedAddress(account, "18446744073709551615");
const scoped = await soran.reverse("nova", m420);
const primary = await soran.primaryOf(m420);
// m0, m420, mMax and account each identify a different lookup input.
```

These example addresses are illustrative; they do not promise an elected name. The SDK decodes the M address and calls `reverse_muxed(namespace, account, id)` or `primary_name_muxed(account, id)` on Universal Lookup. It preserves the ID as an exact u64, never a rounded JavaScript number. Direct mode rejects M identity reads; it cannot emulate them by probing the namespace Resolver.

A Primary record is elected by its address. Holders cannot elect a primary for a destination they do not control merely because they own a name that points there.

## Discovery scope

`reverseLookup` tries Primary first, then ordered namespace candidates. Candidates can come from its argument, `reverseNamespaces`, or a configured indexer hint. `reverseNames` checks those candidates and includes a verified Primary when available. Neither method enumerates every namespace on chain.

The old HTTP `/v1/reverse/:address` route is a **holder hint**, not the source of these verified reverse answers. Holdings and reverse records answer different questions.

## Absence and failures

For G/C addresses, a successful `primaryOf` returning `null` means there is no currently verified election returned by Primary. The existing Primary ABI may hide failed dependent proof reads behind `None`, so even this direct method cannot distinguish every absence from every internal failure. Resolver reverse has a similar limitation. A nonempty answer is independently forward-checked.

Lookup-level errors, including missing Primary configuration, still throw. `reverseLookup` and `reverseNames` can recover from a Primary failure by probing namespace candidates; failed namespace probes are not fabricated empty results.

For M addresses, missing elections and proven stale forward matches return `null`. Malformed records, failed capability probes, unavailable dependencies and unsupported ABIs fail; they do not authorize a base-G fallback. The stored Registrar, Resolver and generation must match current routing and the exact M payment. An M Primary must also match the current verified M reverse election in its namespace.

`primaryId` configures the G/C Primary path. A custom Primary must match the Registry anchor, and in universal mode an explicitly supplied ID must match Lookup's configured Primary. M Primary is stored in Lookup itself and does not depend on this older Primary contract or its pin. Use the [Holder SDK](/holder/managing-your-name#muxed-display-names) for address-authorized elections.
