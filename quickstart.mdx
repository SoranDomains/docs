Resolve a Soran name into its complete payment instructions, then recheck them before sending. Reading requires no wallet or signing key.

This guide uses **Lookup 0.10.2**, Stellar SDK 17 and the current [testnet deployment](/reference/release-status).

## Configure one shared reader

Install Lookup 0.10.2 with Stellar SDK 17:

```bash
npm install @sorandomains/lookup@0.10.2 @stellar/stellar-sdk@^17
```

Supply the current Registry, Lookup and Primary together:

```ts
import { Soran } from "@sorandomains/lookup";

const soran = new Soran({
  network: "testnet",
  registryId: "CCSORANDPQINYOYB5SVO45WJP2LBBYKC72HHUIRVXB4J6RUZKDAUW7G4",
  lookupId: "CDSORANQAJK35UV2HR63CMB6M5NYISHMUBTB6EQY2CZ3Y7HJDIOHRJWA",
  primaryId: "CCSORAN7Y7ICQK2MBSVCJT3BUN5EHXKDKSTMGVB6QWSYXWMMLG2WIFJ6",
  reverseNamespaces: ["nova"],
});
```

Universal Lookup is the default shared reader. It checks the namespace's current on-chain routing and finds its Resolver for you. A missing Lookup configuration throws `CONFIG`.

## Read the whole payment instruction

Start with a [live testnet name](/live-examples). Read its address and memo together:

```ts
const payment = await soran.resolvePayment("Alice.Nova");
console.log(payment.address, payment.memo);

// Display both fields for review, then recheck near confirmation.
if (!(await soran.verifyPayment("alice.nova", payment))) {
  throw new Error("Payment instructions changed; review them again");
}
```

Preserve **both fields** when constructing the payment. If the memo type is `id`, `text` or `hash`, include its exact type and value. Refuse to send if your payment flow cannot carry it. Memo IDs are decimal strings; never convert them to JavaScript numbers.

| Address | How to use it |
| --- | --- |
| `G...` account | Use a classic Stellar payment and the returned memo, if any. |
| `M...` muxed account | Use the full M address in a compatible payment flow. Its embedded ID remains part of the destination; the memo is `none`. |
| `C...` contract | Use the appropriate contract/token transfer flow. The memo is `none`. |

A Soran memo of `none` does not override an account's memo-required setting. A classic transaction has only one memo, so split payments that need different memos. Never strip an M address to G or turn its embedded ID into a transaction memo. See [payment destination examples](/concepts/payment-destinations).

A successful read is a point-in-time answer. Rechecking catches stale client data; it cannot prevent a later record change before a separate payment settles.

## Read ownership and display names separately

```ts
const name = await soran.nameMetadata("alice.nova");
const namespace = await soran.namespaceMetadata("nova");
const displayName = name ? await soran.primaryOf(name.holder) : null;
```

`nameMetadata` can return `null`. When a record exists, `holder` identifies its owner and `builtinAddress` is its Registrar target. Either can differ from the effective payment address. Primary and reverse names identify an account; they do not identify an individual customer memo on a pooled exchange account.

Use [namespace assurance](/sdk/assurance) to assess Resolver provenance. It does not freeze holder records or remove Lookup governance and RPC trust.
