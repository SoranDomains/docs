On-chain state is the source of truth for namespace ownership, name lifecycle and payment instructions. A Soran SDK or hosted database does not decide the destination. Those facts still depend on the deployed code and the RPC through which you read it.

## Contract authority

Registry has no upgrade, forced reassignment or platform revocation method in the reviewed implementation. Allocator adjudicates unclaimed namespaces; its allocation authority cannot overwrite an already owned Registry node.

Namespace owners govern issuance and eligible unlocked Registrar/Resolver implementations. Holders control their own records and permitted transfers. A namespace owner, a holder and a payment recipient are separate roles. Completed permanence constrains namespace code and routing; [no expiry alone does not](/concepts/ownership-guarantees).

Universal Lookup is a shared **governed** read contract. It can change code immediately after an authorized exact-hash proposal. Its stable address and ABI version do not remove this trust boundary.

## What reads verify

Universal Lookup follows current Registry routing and validates supported dependencies, name activity, generation, and complete payment values. A missing or invalid configured payment instruction is an error, not a reason to use an old address. Its metadata methods let an explorer inspect ownership independently from payment success.

Reverse and Primary answers must be canonical and match current forward resolution. They identify an account, not a person or memo customer. The underlying immutable Primary and Resolver reverse APIs can return `None` after a failed internal proof; `None` is therefore not a precise diagnosis of every possible dependency failure. A returned name is checked again.

The SDK checks Lookup's Registry anchor and version. This is compatibility validation, not proof that custom or upgraded code is honest. You also trust the network configuration and RPC response. Separate SDK calls can observe different ledgers; only one contract invocation shares one simulation snapshot.

## Hosted discovery and history

An indexer finds candidates and archives events. The SDK verifies current holdings candidates on chain, but an indexer can omit names. Pagination and coverage expose continuation, gaps and freshness; they cannot prove an indexer omitted nothing.

History, registration timestamps, directory listings and profile labels are informational or user-authored data. Profile text being written on chain does not prove its claims true. Escape it, validate links and never treat it as instructions.

## Hosted services and custody

The console, HTTP API, webhooks and optional managed services help operate the contracts. Self-custody writes are signed by your wallet. A platform-operated namespace instead uses the deployment's operating signer; do not confuse console access with on-chain authority.

Billing and the marketplace apply **when enabled on a deployment**. Hosted subscriptions do not create a yearly ownership levy in the naming contracts. Marketplace payment escrow is operator-custodied and separate from the Allocator's on-chain namespace-claim escrow.

You can call the contracts through another RPC without the hosted app. Continued availability still requires accessible contract state, storage upkeep/restoration, a working RPC and supported contract code. It is not a promise that every dependency keeps running without maintenance.
