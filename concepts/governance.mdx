description: "Which contracts can change, what zero delay means, and which addresses remain stable."

Universal Lookup has **no mandatory upgrade delay**. The selected policy for Allocator contract upgrades is also zero delay, but that change is **not live yet**. The deployed testnet Allocator still requires a 24-hour wait to install the replacement. Namespace claim windows, objections, reopening rules and namespace permanence are unchanged.

## Universal Lookup upgrade flow

1. Governance authorizes `propose_upgrade(wasm_hash)` for one exact code hash.
2. The proposal records `execute_after` as the current ledger timestamp. It is immediately eligible.
3. Anyone may call `execute_upgrade(expected_hash)`. The hash must equal the pending proposal.
4. A successful execution replaces the contract's Wasm at the same contract address and consumes the proposal. A failed replacement rolls back the transaction.

Governance can call `cancel_upgrade()` while a proposal is pending, but there is no guaranteed time in which cancellation can beat immediate execution. Read `governance()`, `upgrade_delay()` and `pending_upgrade()` when assessing a deployment.

A stable Lookup address makes integration routing consistent. Its Registry/version checks establish reported wiring and ABI compatibility, **not a pin of the executable code**. Integrators requiring reviewed code need their own current-code verification policy.

## Allocator upgrade policy (pending installation)

After the replacement is installed and verified:

1. Governance authorizes `propose_upgrade(new_wasm_hash)` for one exact Wasm hash. The proposal stores `eta` as the current ledger timestamp.
2. Anyone may call `execute_upgrade()` immediately. It uses the stored proposal's hash; the caller cannot substitute another hash.
3. Successful execution replaces the Wasm at the same Allocator address and consumes the proposal. A failed replacement rolls back the transaction.

Governance retains `cancel_upgrade()`. Only one proposal can be pending, and it must be cancelled before a different one is proposed. With zero waiting, cancellation has no guaranteed review window before permissionless execution.

Installing this policy still requires one **24-hour wait under the currently deployed code**. Replacing the pending proposal with the revised code hash starts a fresh wait; editing the replacement code does not shorten an existing proposal's recorded `eta`. See [release status](/reference/release-status) for installation status.

This changes only contract-upgrade timing. A namespace application still completes its configured public claim window, objections retain their existing rules, and governance reopening proposals still wait one full allocation window. Storage compatibility and fee/credit obligations must also survive a code upgrade; keeping the same address does not migrate incompatible state.

## Other contracts

| Contract | Upgrade boundary |
| --- | --- |
| Registry | No upgrade method in the reviewed implementation; replacing a Registry means a new deployment and configuration |
| Allocator | Current testnet code requires 24 hours for upgrades; the pending replacement makes future upgrade proposals immediately eligible. Claim, objection and reopening windows remain separate |
| Registrar and Resolver | The namespace owner can change eligible unlocked contracts; permanence and upgrade taint constrain that ability |
| Primary | No code upgrade entry point in the reviewed implementation |
| Universal Lookup | Governed exact-hash code replacement with zero mandatory delay |

Replacing a Resolver with a different contract creates separate storage. Its records do not migrate automatically. An in-place upgrade preserves the address, but compatible storage and access rules are still required. A permanently locked old Resolver cannot be upgraded to gain memo support.

The **6 September native-claim deployment** created a fresh stack whose immutable Registry pins its native Resolver factory baseline. The **7 September muxed identity upgrade** changes only Universal Lookup's code at its existing address; it adds exact-M election storage without replacing Registry, Resolver or Primary. Registry salt version `1` and namespace-and-role binding remain unchanged. Integrations must use the matching Registry, Lookup and G/C Primary anchors. See [release status](/reference/release-status) and [namespace address prediction](/concepts/names-and-namespaces#namespace-contract-addresses).
