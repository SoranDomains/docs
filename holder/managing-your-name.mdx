description: "Publish an atomic on-chain address and optional memo, profile records and account display names."

The Holder SDK writes payment and name records to the current namespace contracts. Universal Lookup is the shared read entry point and, with the muxed identity extension, stores M display-name elections. These examples target Holder 0.6.0 with Stellar SDK 17. See [release status](/reference/release-status) for the matching testnet contracts.

<Note>
Use published Holder **0.6.0** for native claims and receipt recovery. It verifies Registrar attestation and deployed code against sufficiently recent RPC ledger context before accepting receipt results. It adds full-M display-name elections, retains the receipt-verification checks introduced in 0.5.1, native claims and lifecycle flows from 0.5.0, and M payment writes from 0.4.0. Contract pins are unchanged; see [release status](/reference/release-status).
</Note>

```ts
import { SoranHolder } from "@sorandomains/holder";
const me = new SoranHolder({
  signer: walletSigner,
  registryId: deployment.registryId,
  primaryId: deployment.primaryId,
  rpcUrl: deployment.rpcUrl,
  passphrase: deployment.passphrase,
});
```

`walletSigner` implements `publicKey()` and `signTransaction(xdr, options)`. A backend can use the package's `keypairSigner` with a securely supplied secret. Never put signing keys in frontend configuration.

This `TxSigner` flow uses a classic G account as the transaction source. C support as a payment recipient or contract holder does not provide arbitrary contract-wallet signing through this adapter. A contract-owned name needs a compatible contract authorization integration; M destinations are payment routes, not signer identities.

## Claim a username

Use `claimQuote`, `createClaimIntent` and `claim` for native registration. The quote includes the owner’s price, treasury, admission rules and exact versioned terms. The user reviews and authorizes both ownership and the full receiving destination; issuance, fee, route and receipt commit together. See the [complete signup and recovery examples](/owner/automatic-claiming#claim-from-your-application). This is separate from applying for a top-level namespace.

## Address and memo together

```ts
await me.setPayment("alice.nova", {
  address: exchangeAddress,
  memo: { type: "id", value: "123456" },
});

// Explicitly remove the memo while selecting the complete destination:
await me.setPayment("alice.nova", {
  address: myAddress,
  memo: { type: "none" },
});
```

The native Resolver updates the address and memo atomically on chain. No separate payment contract or database stores these instructions. Memos are optional: untouched ordinary records resolve with `none`. A configured instruction that is missing or invalid fails rather than reverting to an ordinary address.

`setRecord(name,address)` is the address-only native Resolver convenience for memo-free records. A required memo or muxed destination must be changed through `setPayment`; the contract refuses an address-only write that would discard its routing information. `setAddress(name,address)` changes the Registrar's built-in target, which may be overridden by current Resolver instructions; the SDK requires a current direct memo-free payment before preparing this convenience operation; muxed destinations must use `setPayment`. Use `resolvePayment` to read the effective pair.

G destinations support None, ID, text and hash memos; M and C support None only. Pass the full M address to `setPayment`; the SDK submits `set_muxed` with its exact base G account and u64 ID. It never substitutes a transaction memo. The Holder SDK checks exact [payment constraints](/sdk/resolving-names). See [complete examples for each address and memo type](/concepts/payment-destinations).

## Profile records

```ts
await me.setProfile("alice.nova", {
  org: "Alice Co",
  url: "https://alice.example",
});
await me.setText("alice.nova", "description", "My profile");
await me.clearText("alice.nova", "description");
```

`setProfile` submits one transaction per key sequentially; a partial failure can leave earlier keys written. Ordinary text is overwrite-only, and `clearText` writes an empty value. Standard profile readers treat that as unset. Do not clear a payment memo through arbitrary text; use `setPayment`.

## Account display names

```ts
await me.setReverse("alice.nova");
await me.setPrimary("alice.nova");
```

Reverse and Primary writes require the address's authorization and a current forward match. Name ownership alone does not authorize identity writes for someone else's destination account. The Primary Registry anchor is checked before signing; custom deployments need matching configuration.

`clearReverse(namespace)` and `clearPrimary()` remove G/C elected display records. These account elections do not distinguish individual customer memos. Changing a payment destination to M can make a previous G/C reverse or Primary selection stop verifying. Use the dedicated M methods below to elect a name for the complete muxed address.

## Muxed display names

<Note>
Holder 0.6.0 is published; the testnet Lookup reports `muxed_identity_version() == 1`. Existing G/C election methods and all contract addresses remain unchanged. See [release status](/reference/release-status) for verification.
</Note>

Configure `lookupId` alongside the matching Registry and network. The testnet preset supplies it; a custom Registry or passphrase does not inherit an unrelated Lookup pin. The signer must control the **base G account** of the M address. A customer who only receives an exchange deposit address cannot sign for the exchange.

```ts
const me = new SoranHolder({
  signer: walletSigner,
  registryId: deployment.registryId,
  lookupId: deployment.lookupId,
  rpcUrl: deployment.rpcUrl,
  passphrase: deployment.passphrase,
});
const muxedAddress =
  "MA7QYNF7SOWQ3GLR2BGMZEHXAVIRZA4KVWLTJJFC7MGXUA74P7UJUAAAAAAAAAABUTGI4";

// The active name must already resolve to this exact M address.
await me.setReverseMuxed("customer420.nova", muxedAddress);
// Optional: select the same verified reverse name across namespaces.
await me.setPrimaryMuxed("customer420.nova", muxedAddress);
```

Each call is a separate wallet-authorized transaction. If the first succeeds and the second is cancelled, the namespace reverse selection remains valid. Review replacement of an existing selection: changing or clearing the reverse means a Primary using the old reverse no longer verifies while that mismatch persists. Claiming or publishing a destination does not elect these names automatically.

```ts
await me.clearReverseMuxed("nova", muxedAddress);
await me.clearPrimaryMuxed(muxedAddress);
```

These four methods call Universal Lookup. They bind the name or namespace, base G and exact u64 ID in the authorization. They do not edit payment instructions or strip the M address to G. ID `"0"` is distinct from the base G account. A transferred or reissued name has a new generation and needs a fresh election.

Operators can maintain existing elections with the contract's permissionless `touch_reverse_muxed` and `touch_primary_muxed` calls. A touch does not create an election or make stale proof valid. See the [contract ABI](/api/onchain-resolution#muxed-identity-extension) and [stored records](/reference/contract-storage#muxed-identity-storage).

## Name transfer

```ts
await me.proposeNameTransfer("alice.nova", recipientAddress);
const pending = await me.pendingNameTransfer("alice.nova");
await me.cancelNameTransfer("alice.nova");
```

The intended recipient can use `acceptNameTransferWithDestination` with a reviewed `TransferIntent` to accept and initialize a complete G/M/C destination atomically. It binds the pending proposal, sender, recipient, generation and expiry, preserves the name’s expiry and advances generation. The older `acceptNameTransfer` method selects the recipient’s ordinary default route; it does not copy the previous holder’s memo or muxed destination. Policy and activity gates apply to both. Transferring a name is separate from transferring its entire namespace.

## Renew a finite name

`renewalPreview(name)` returns the exact generation and stored destination, including `active:false` for an expired name. It does not make an expired name resolve for live payments. Use `renewName` with a canonical `RenewIntent` binding the holder, generation, existing expiry, immutable term and accepted new-expiry bounds.

Renewal is independent of public-claim pause, app eligibility and namespace ownership epochs. It has no separate username renewal fee; network/storage costs still apply. It is allowed only within the last `min(30 days, term)` of a finite lease or after expiry until reissuance wins. It extends by one immutable term from `max(now, expiry)` and cannot exceed 100 years from execution time. Zero-term names and stale/reissued generations are ineligible. Owner reclaim rights remain subject to the namespace policy.

See the [exact lifecycle ABI](/api/native-claiming#transfer-and-renewal) before constructing a transfer or renewal intent.

## Errors and uncertain submissions

Simulation catches many permission/policy failures before signing. Existing Holder methods use `HolderError`; native methods use `NativeClaimError` with `kind`, optional contract code/name and `txHash`. A transaction that reached the network can carry that recovery hash. Check uncertain inclusion before retrying. Preflight success does not guarantee later submission success or remove its network fee.
