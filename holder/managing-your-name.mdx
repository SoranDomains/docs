---
title: "Managing your name"
description: "Publish an atomic on-chain address and optional memo, profile records and account display names."
---

The Holder SDK writes to the current namespace contracts. Lookup remains the shared read entry point. These examples target Holder 0.4.0 with Stellar SDK 17. See [release status](/reference/release-status) for the matching testnet contracts.

<Note>
Holder **0.4.0** is published. M-address writes require this version; older packages do not submit `set_muxed`. You can also publish a destination through the app or its [on-chain Resolver methods](/api/onchain-resolution).
</Note>

```ts
import { SoranHolder } from "@sorandomains/holder";
const me = new SoranHolder({
  signer: walletSigner,
  registryId: deployment.registryId,
  primaryId: deployment.primaryId,
  rpcUrl: deployment.rpcUrl,
  passphrase: deployment.passphrase,
});
```

`walletSigner` implements `publicKey()` and `signTransaction(xdr, options)`. A backend can use the package's `keypairSigner` with a securely supplied secret. Never put signing keys in frontend configuration.

This `TxSigner` flow uses a classic G account as the transaction source. C support as a payment recipient or contract holder does not provide arbitrary contract-wallet signing through this adapter. A contract-owned name needs a compatible contract authorization integration; M destinations are payment routes, not signer identities.

## Address and memo together

```ts
await me.setPayment("alice.nova", {
  address: exchangeAddress,
  memo: { type: "id", value: "123456" },
});

// Explicitly remove the memo while selecting the complete destination:
await me.setPayment("alice.nova", {
  address: myAddress,
  memo: { type: "none" },
});
```

The native Resolver updates the address and memo atomically on chain. No separate payment contract or database stores these instructions. Memos are optional: untouched ordinary records resolve with `none`. A configured instruction that is missing or invalid fails rather than reverting to an ordinary address.

`setRecord(name,address)` is the address-only native Resolver convenience for memo-free records. A required memo or muxed destination must be changed through `setPayment`; the contract refuses an address-only write that would discard its routing information. `setAddress(name,address)` changes the Registrar's built-in target, which may be overridden by current Resolver instructions; the SDK requires a current direct memo-free payment before preparing this convenience operation; muxed destinations must use `setPayment`. Use `resolvePayment` to read the effective pair.

G destinations support None, ID, text and hash memos; M and C support None only. Pass the full M address to `setPayment`; the SDK submits `set_muxed` with its exact base G account and u64 ID. It never substitutes a transaction memo. The Holder SDK checks exact [payment constraints](/sdk/resolving-names). See [complete examples for each address and memo type](/concepts/payment-destinations).

## Profile records

```ts
await me.setProfile("alice.nova", {
  org: "Alice Co",
  url: "https://alice.example",
});
await me.setText("alice.nova", "description", "My profile");
await me.clearText("alice.nova", "description");
```

`setProfile` submits one transaction per key sequentially; a partial failure can leave earlier keys written. Ordinary text is overwrite-only, and `clearText` writes an empty value. Standard profile readers treat that as unset. Do not clear a payment memo through arbitrary text; use `setPayment`.

## Account display names

```ts
await me.setReverse("alice.nova");
await me.setPrimary("alice.nova");
```

Reverse and Primary writes require the address's authorization and a current forward match. Name ownership alone does not authorize identity writes for someone else's destination account. The Primary Registry anchor is checked before signing; custom deployments need matching configuration.

`clearReverse(namespace)` and `clearPrimary()` remove the elected display records. These identify G/C accounts, not individual customer memos or muxed IDs. Changing a payment destination to M can make a previous reverse/Primary selection stop verifying; use a direct account destination for account identity.

## Name transfer

```ts
await me.proposeNameTransfer("alice.nova", recipientAddress);
const pending = await me.pendingNameTransfer("alice.nova");
await me.cancelNameTransfer("alice.nova");
```

The intended recipient accepts with `acceptNameTransfer` and its own signer. Policy and activity gates apply. Acceptance advances ownership generation, invalidating prior-holder records. Transferring a name is separate from transferring its entire namespace.

## Errors and uncertain submissions

Simulation catches many permission/policy failures before signing. Contract failures are typed `HolderError`s; a transaction that reached the network can carry `txHash`. Check uncertain inclusion before retrying. Preflight success does not guarantee later submission success or remove its network fee.
