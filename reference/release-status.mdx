- Native XLM asset contract: `CDLZFC3SYJYDZT7K67VZ75HPJVIEUVNIXF47ZG2FB2RMQQVU2HHGCYSC`.
- Namespace application fee: `50000000000` base units, with 7 decimals = **5,000 XLM**.

The [namespace fee configuration transaction](https://stellar.expert/explorer/testnet/tx/6bb169c931a2802dd3419729f24e3d11c382b6b2d19fb2e59fd77a8933badc0e) sets the upfront escrow policy. Award pays the recipient; rejection and stuck cancellation return 100%; withdrawal and expiry return 80%. Settlement may create protected pull credit if delivery fails. See [claim outcomes](/concepts/claiming-a-namespace).

The Allocator timing change requires an in-place code upgrade. Replacing the earlier pending proposal with the revised Wasm hash restarts the current 24-hour wait. Zero waiting applies only after that replacement executes and its code is verified. The Allocator address and its retained records remain the same; this does not redeploy the Registry. Governance still proposes the exact hash, execution remains permissionless, and cancellation and the single-pending-proposal rule remain. See [governance and upgrades](/concepts/governance#allocator-upgrade-policy-pending-installation).

The revised proposal was confirmed at ledger **4,539,796** on 6 September in [this proposal transaction](https://stellar.expert/explorer/testnet/tx/1fb5fff74210841be222950339c76ab1018fbc3f76bb480c2fc71ccef1f28416). It selects Wasm `9480a4f980de9df0a31652b0b64c54d5c5e1979745cc8c4fc486624b9c177e40`, combining the XLM payout correction and zero-delay policy. Its earliest activation is **7 September 2026 at 19:22:47 UTC** (20:22:47 Lagos). This is a pending proposal, not confirmation that the new code is active.

A **username** fee is separate. A namespace owner can configure free claims or a flat XLM amount paid directly to their G treasury, atomically with issuance and complete payment instructions. There is no username approval escrow or mandatory annual ownership charge. The bounded holder renewal has no separate username renewal fee. Network execution, storage and restoration costs remain separate. See [automatic claiming](/owner/automatic-claiming).

The initial native-claim packages—Lookup 0.7.0, Holder 0.5.0, Owner 0.7.0 and MCP 0.7.0—were downloaded and matched the tested release bytes by **12:35:18 UTC** on 6 September. Holder **0.5.1** was subsequently verified from npm at **18:13 UTC**, with its installed code matching the reviewed patch. Use 0.5.1 for current Holder integrations. These versions use Stellar SDK 17. The previous published release was Lookup 0.6.0, Holder 0.4.0, Owner 0.6.0 and MCP 0.6.0. That release already supports muxed payments; it does not provide the new native username claim interface or the new default deployment.

Holder 0.5.1 verifies Registrar attestation and executable with RPC ledger context at least as recent as each receipt read or transaction confirmation, including reads that find no receipt. Unavailable or older context stops recovery; preserve the original request and transaction hash. A verified receipt remains historical success, not proof of current ownership. See [receipt recovery](/owner/automatic-claiming#recover-before-replacing-a-request).

MCP **0.7.1** is published with an exact Holder 0.5.1 dependency for local tools. Hosted MCP remains the separately verified **0.7.0** read-only service. None of these client updates changes the contract addresses or deploys later contract source fixes.

The [quickstart](/quickstart) pins Registry, Lookup and Primary explicitly. Missing Lookup configuration throws `CONFIG`; resolution never silently falls back to direct reads. A successfully read supported version selects the matching ABI. Unknown versions and failed reads do not trigger a downgrade.
