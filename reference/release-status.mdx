Soran is available on **Stellar testnet**. Mainnet is not available yet. This page reflects contract, app and SDK releases verified on **1 October 2026**. The [deployment manifest](https://raw.githubusercontent.com/SoranDomains/docs/main/reference/deployments/testnet.json) records each verification separately.

<span id="verified-claim-behavior" />

The current release includes profiles and social links, complete Stellar payment destinations, addresses on 14 additional networks, and one subname level such as `mail.alice.yourbrand`. **Availability depends on the namespace:** shared contract support and published SDKs do not automatically upgrade an existing namespace or enable its policies.

| Capability | What you need |
| --- | --- |
| Profiles and social links | A compatible Resolver and the current holder’s signature |
| Stellar payment destinations | Complete G/M/C instructions, including any required memo or muxed ID |
| Additional network addresses | A compatible Resolver and an owner-enabled network allowlist |
| Subnames | Compatible Registrar and Resolver code, then owner-enabled creation |
| Reverse and Primary names | The receiving identity’s authorization and a current forward match |

For a working integration, start with the [quickstart](/quickstart) or try the [live examples](/live-examples).

## Network, versions and fees

| Setting | Value |
| --- | --- |
| Network | Stellar testnet |
| RPC | `https://soroban-testnet.stellar.org` |
| Network passphrase | `Test SDF Network ; September 2015` |
| Public namespace application | **5,000 XLM** upfront |
| Username claim | Free or a flat XLM price set by the namespace owner |

The namespace application fee goes into Allocator escrow. Award pays the configured recipient; rejection or stuck cancellation refunds 100%; withdrawal or expiry refunds 80%. See [namespace claim outcomes](/concepts/claiming-a-namespace).

A username fee goes directly to the owner's configured treasury when the claim succeeds. There is no username approval escrow or mandatory annual Soran ownership fee. Transaction and storage costs are separate. Read the namespace's current quote before showing a price; see [automatic claiming](/owner/automatic-claiming).

## Display-name transaction costs

Setting or clearing a display name in Lookup or Primary no longer renews the shared Wasm code. These writes still pay Stellar transaction costs and any required record or instance storage rent. Explicit maintenance renews the shared code in bounded increments, paid by whoever submits that maintenance transaction. This update does not add automatic fee sponsorship.

Reading a name through RPC simulation does not submit a transaction or charge an on-chain fee. A lookup invoked inside a submitted transaction contributes to that transaction's resource costs. Always simulate writes for a current fee estimate.

The [Lookup upgrade](https://stellar.expert/explorer/testnet/tx/57b77ddfbcd3aa34eb71b41a03c412449a09cca567826b532de63b9ed2cd4d1c) and [Primary upgrade](https://stellar.expert/explorer/testnet/tx/42169053b6d19d516970cf54095b6d249cff7e9499b6c1fbdbfaa9b218c96d33) are confirmed. That release preserved existing records and contract methods. See [storage lifetime](/reference/contract-storage#ttl-and-restoration).

## Namespace-funded sponsorship

The Funding contract and hosted sponsorship API are live on testnet. **Sponsorship is optional:** the namespace owner must fund and enable a position, and the claiming app must use the sponsorship flow. Existing self-pay flows keep their current fee payer.

A namespace owner can sponsor successful username claims, reverse elections and primary-name elections. The relayer pays Stellar's network fee; the Funding contract settles the agreed charge from the owner's position only when the action succeeds. A separate username price remains payable by the claimant. Sponsorship does not include account creation or automatic contract maintenance.

Pricing uses a fixed quote based on live Stellar fee estimates. The agreed amount is charged only when the action succeeds, and Soran retains any savings against the actual network fee. There is no separate refund transaction or later debit. The agreed quote must fit the owner’s configured spending limits.

The [Funding deployment](https://stellar.expert/explorer/testnet/tx/27984e617be4437d636a69e603908a0412a009386d336a6e8bfc1d3fd76c3322) is confirmed. Existing naming contract addresses are unchanged.

## Subnames and network addresses

The [1 October Lookup upgrade](https://stellar.expert/explorer/testnet/tx/381229a5c15622574ef4323832ae556ec96ecbaa1f849652b517a53f9f208ce0) and [Primary upgrade](https://stellar.expert/explorer/testnet/tx/bfe07f07fa68e6c7e349fe78e0ff0547b403668b2eecad679b59d977d555f0cf) installed shared subname support. Lookup also supports explicit network-address reads. Their existing addresses are unchanged.

Registry governance [selected compatible Registrar and Resolver templates](https://stellar.expert/explorer/testnet/tx/9bdb67c418a9fbcf5701dd7df5accf4bcd71631c387429f3c4ff70ef2a960958) for new namespace deployments. **Existing namespace contracts and policies were not changed by this rollout.** The console and HTTP API include the corresponding interfaces, and the published core SDKs expose the read and write methods.

For an existing namespace, its owner must install the compatible contracts and choose the policy. Additional networks start disabled. Subnames start with creation disabled; enabling creation is separate from installing the code. A subname remains controlled by its parent holder and is not independently transferable.

Additional network IDs describe destination mainnets, even while Soran runs on Stellar testnet. Publishing an address does not send funds or bridge assets. Stellar retains its complete address-and-memo flow.

### Name status and history reads

The [9 September Lookup upgrade](https://stellar.expert/explorer/testnet/tx/34ac6a1189a83f6ea33692b4a9dca65324e147653b9ef8d74800c6eedc7ff907) keeps the same contract address, storage and existing methods. `name_status` distinguishes missing namespaces, missing Registrars, unregistered names, active names and expired records in one observation. Existing payment error codes remain compatible.

The [10 September batch optimization](https://stellar.expert/explorer/testnet/tx/5c444700a524c0a2454ad94cd3822562e7774a5d16c219e6c0599046d6910c91) keeps all contract addresses unchanged. `reverse_names` accepts up to **32** G/C/full-M identities in one namespace; `primary_names` accepts up to **16** across namespaces. Current native contracts combine related reads and share namespace verification work while still checking each live forward destination. Lookup 0.11.0 history helpers split calls when a host budget limit requires it and preserve each row's ledger/time. See [contract methods](/api/onchain-resolution#history-screens-and-multiple-addresses), [SDK examples](/sdk/reverse-and-primary#history-screens) and [exact JavaScript/XDR shapes](/reference/lookup-decoding#status-and-batch-shapes).

The current SDK release preserves these history methods and complete Stellar payment reads.

## Allocator upgrade

The Allocator records [case-specific rulings and explanations](/reference/namespace-objections) on chain. Code-upgrade execution and cancellation bind the exact reviewed code hash. Reopening cancellation and execution now bind the [exact proposal identity](/reference/namespace-objections#reopening-proposals), so a replacement proposal needs a new review. The [8 September upgrade](https://stellar.expert/explorer/testnet/tx/a9c77709a1a4e51fa4a5ca74647e332302f629ef53578bb3bc912fd7e29ca9c3) keeps the same contract address and storage schema `4`.

Those upgrades added case-specific rulings, removed the mandatory wait for new governance-approved code proposals and fixed XLM settlement to G accounts that do not yet exist. A payout can create the account when it meets the required reserve; if the transfer fails, the recipient receives a recoverable credit. The upgrades are recorded separately in the deployment manifest.

The 10 September governed migration also upgraded Allocator code in place and retained its escrow. Namespace claim and objection windows, the 5,000 XLM fee and refund entitlements remain unchanged. See [governance and upgrades](/concepts/governance#allocator-upgrade-flow).

## Governed testnet deployment

The 10 September migration preserved the Universal Lookup and Allocator addresses. Registry, Primary and Nova’s Registrar and Resolver use the successor addresses above. Later upgrades retain these addresses. Use the current core SDK versions with this deployment; MCP manages its own dependency versions.

The active naming contracts support authorized upgrades at the same address. Namespace Registrar and Resolver upgrades require the current namespace owner and protocol approval for the exact contract role and code hash. The governed testnet does not permit irreversible code locks. Name expiry and owner reclaim policy remain separate settings. See [governance](/concepts/governance).

The migration retains existing names, payment destinations, exact memo values and full muxed routing IDs. Display-name lookups verify the complete destination; an M destination is not a base-G election. Pending namespace applications retain their original claim windows, escrow and refund entitlements.

Keep original saved claims and transaction hashes. Owner and Holder can verify historical receipts through `recoverHistoricalClaim(originalIntent, { lookupId })` once canonical Lookup confirms the sealed successor. A missing or unavailable receipt does not authorize an automatic retry. Source receipts remain at their original Registrar.

New clients also enforce a shared network-fee ceiling for writes and storage restoration; see [client configuration](/sdk/installation#write-client-fee-limit).
